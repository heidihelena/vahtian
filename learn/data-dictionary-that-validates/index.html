Clean and prepare your data

“How do I build a data dictionary that validates?”

Define your variables and their allowed values before you collect, so cleaning does not become your analysis.

A data dictionary is the contract your data has to meet: one row per variable, saying what it is called, what type it is, what values are allowed, and whether it identifies a person. Set it before collection and the software rejects bad entries at the source. Skip it and you meet every problem at once, the night before analysis.

By Heidi Andersén, MD, PhD · Updated 18 July 2026 · 6 min read

The problemCleaning becomes the analysis

You open the spreadsheet to run your first test and find ages typed as words, a sex column with nine spellings, dates in three formats, and blank cells you cannot tell from real zeros. None of it was caught when it was entered, so all of it lands on you now. A data dictionary moves that work to the start, where it is cheap, and lets the data-entry tool enforce it.

What it isOne row per variable

A data dictionary (REDCap calls it the instrument, other tools call it a codebook) is a table with one row for every variable you will collect. The columns that carry the work:

  • Variable name: short, lower-case, no spaces (age_years, not “Age (years)”).
  • Field type: text, radio, dropdown, checkbox, date, yes/no, calculated.
  • Label: the human question shown at entry.
  • Choices: coded options, not free text (1, Male | 2, Female), so answers are consistent and analysable.
  • Validation: a type and range the entry must pass (integer, a date format, a min and max).
  • Identifier?: mark any field that could identify a person. This flag drives what you strip before you share.

A minimal dictionary (REDCap-style)

variable       type    label                choices / validation    identifier?
record_id      text                         (auto)                  no
age_years      text    Age in years         integer, 18-120         no
sex            radio   Sex at birth         1, Male | 2, Female     no
consent_date   text    Date of consent      date_dmy                no
initials       text    Participant initials -                       yes

The age_years rule (integer, 18-120) refuses “forty” and “220” at entry. The coded sex choices refuse a tenth spelling. initials is flagged as an identifier, so you know to remove it before sharing.

ValidationRules that catch the error at entry

Validation is what makes the dictionary earn its place. Set the type and range once and the tool refuses anything that fails: an integer field will not accept text, a date_dmy field will not accept 13/25/2026, a min and max fence out impossible values. Use coded choices instead of a free-text box wherever the answer is a category. Mark the fields that must not be blank as required. None of this proves the data is correct, but it removes whole classes of error before they reach you.

ThenRead it into R or Python

A dictionary-backed export is already clean and typed, so import is the easy part.

R

library(REDCapR)
d <- redcap_read(redcap_uri = uri, token = token)$data
# or from a CSV export:
d <- readr::read_csv("data.csv")

Python

import pandas as pd
d = pd.read_csv("data.csv")

ChecklistBefore you open recruitment

Five checks

  • Every variable has a name, a type, and a label.
  • Every category field uses coded choices, not free text.
  • Numbers and dates have a validation type and a plausible min and max.
  • Required fields are marked required.
  • Every field that could identify a person is flagged as an identifier.
